# نتیجهٔ آزمون تونل‌های IP بین دو سرور

در ۱۰ نوامبر ۲۰۲۶، دو نمونهٔ IP tunnel از طریق API همین سامانه ساخته و روی هر دو میزبان با systemd اجرا شدند. این آزمون از Backhaul معمولی و حالت TUN استفاده می‌کند.

| نمونه | سرور ورودی و آدرس داخلی | کلاینت و آدرس داخلی | MTU |
|---|---|---|---:|
| `codexcheck` | `65.109.179.222:18443` · `10.200.0.1/30` | `91.107.139.87` · `10.200.0.2/30` | 1400 |
| `codexip` | `65.109.179.222:18444` · `10.201.0.1/30` | `91.107.139.87` · `10.201.0.2/30` | 1400 |
| `codexdirect` | `65.109.179.222` · `10.202.0.1/30` (client) | `91.107.139.87:18445` · `10.202.0.2/30` (server) | 1400 |

هر دو نمونه از Backhaul transport نوع `tun` استفاده می‌کنند و هرکدام یک subnet داخلی جدا دارند. هر دو سرویس در systemd وضعیت active دارند.

## آزمون‌ها

- روی هر دو سمت برای هر دو تونل، رابط TUN آدرس صحیح گرفت.
- ping دوطرفه روی هر دو subnet موفق شد؛ packet loss برابر 0% در هر آزمون.
- روی `codexip`، یک TCP echo آزمایشی فقط برای مدت آزمون روی `10.201.0.2` اجرا شد. از سمت سرور اول یک payload تصادفی 1 MiB فرستاده شد؛ 1 MiB پاسخ برگشت و byte-for-byte برابر بود.
- لینک `codexdirect` برای حالت direct ساخته شد: سرور اول client است و به server روی میزبان دوم dial می‌کند. ping دوطرفه روی `10.202.0.0/30` با packet loss صفر موفق شد.
- دکمهٔ Restart پنل از API با Bearer token اجرا شد؛ سپس وضعیت زنده دوباره active گزارش شد.
- endpoint گزارش‌ها از journal سرویس Backhaul خروجی واقعی برگرداند.
- listenerهای آزمایشی echo پس از آزمون متوقف و فایل‌های موقتشان پاک شدند؛ خود دو تونل باقی ماندند.

## مشاهده و مدیریت از داشبورد

روی هر میزبان سرویس `tunnelmgr.service` فقط به `127.0.0.1:8765` گوش می‌دهد. از رایانه‌ات SSH port-forward را باز کن:

```sh
ssh -L 8765:127.0.0.1:8765 root@65.109.179.222
```

سپس `http://127.0.0.1:8765/` را باز کن. برای پنل سرور دوم، از پورت محلی متفاوت استفاده کن:

```sh
ssh -L 8766:127.0.0.1:8765 root@91.107.139.87
```

و `http://127.0.0.1:8766/` را باز کن. نسخهٔ اولیه از Bearer token استفاده می‌کرد؛ رابط بازطراحی‌شده ورود با نام کاربری و گذرواژه دارد. برای ارتقای نسخهٔ نصب‌شده، گذرواژهٔ حساب‌های قبلی را با `sudo -u tunnelmgr env TUNNELMGR_HOME=/var/lib/tunnelmgr python3 /opt/tunnelmgr/tunnelmgr/tunnelctl.py account password ADMIN_NAME` یک‌بار تنظیم کن.

فرم یکپارچه همهٔ driverهای موجود را دارد و endpointها را با helper محدودشدهٔ Unix socket اجرا می‌کند. برای دو سر یک لینک، شناسه و secret یکسان و آدرس‌های peer معکوس وارد کن. API عمومی نیست.

## direct و reverse

طبق قرارداد فعلی پنل، direct یعنی node A به listener روی node B dial می‌کند؛ reverse یعنی node B به listener روی node A dial می‌کند. `codexdirect` همین حالت direct را نمونه‌سازی می‌کند؛ دو تونل قبلی reverse هستند. هر سه لینک روی همین دو گره فعال‌اند.

## مرز آزمون

در ۱۱ نوامبر ۲۰۲۶ ابزار `scripts/mesh-deploy.py` یک لینک full-mesh مستقیم را روی همین دو نود ساخت. listener روی `91.107.139.87:18444` قرار گرفت و client روی `65.109.179.222` به آن وصل شد. subnet این لینک `10.240.0.0/30` است: آدرس نود اول `10.240.0.1/30` و نود دوم `10.240.0.2/30`.

فرمان `--check` روی هر دو نود سرویس systemd را active دید و ping دوطرفه به peer داخلی موفق شد. secret تصادفی این لینک در `/etc/backhaul/secrets/` با مجوز `0600` ذخیره شده و از مسیر SSH منتقل شد.

این ابزار لینک‌های مستقل را خودکار می‌سازد؛ route بین شبکه‌های پشت نودها یا forwarding برای عبور ترافیک چندپرشی تنظیم نمی‌کند. پروتکل‌های kernel-native دیگر یا Backhaul اصلی نیز در این آزمون نیستند. پورت `18444/UDP` برای listener تازه باید در firewall میزبان/ارائه‌دهنده باز باشد.
